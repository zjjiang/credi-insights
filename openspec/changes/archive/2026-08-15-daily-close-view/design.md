## Context

`daily-imap-ingest` 打通了日推邮件的抓取入库,但把日推 Tab 当成「候车厅」(月账单一到就排空)会让日结失去意义。本设计重构为**两级结算**模型:日结(时效)与对账(权威)都是有价值的终态,日推数据本身即可分析,月账单只是事后盖章。

## Goals / Non-Goals

**Goals:**
- 按日粒度的独立视图,交易被对账后不从按日视图消失
- 日结完整性可信:检测并提示日推覆盖缺口
- 对账后的标签毕业可见;陈旧未对账交易可人工清理
- cron 每早自动关账

**Non-Goals:**
- 不改动已合并的抓取/解析/合并核心逻辑(仅在其上追加覆盖度记录)
- 不做跨月趋势分析(现有月账单看板已覆盖)

## Decisions

### D1: 两级结算 —— 日结 + 对账,而非单一终态

**模型**:
```
交易 → [日结] 次晨日推到达,当日数据完整可分析(时效)
     → [已对账] 月账单 fingerprint 命中,uploadId 填上,银行确认(权威)
```
**理由**:日推的价值就是时效性。若日结只是「等月账单确认」的临时态,日推就没意义。日结是完整终态,对账是事后修正(退款/撤销/外币最终额)。
**替代方案(否决)**:候车厅模型(`uploadId==null` 才在日推 Tab)—— 对账后交易蒸发,日结历史丢失,违背日结初衷。

### D2: 按日 Tab 过滤维度 —— 日期窗口,而非 source

**规则**:按日 Tab 按 `txDate` 分组倒序,不按 `source` 过滤。`uploadId`/`source` 降级为「对账状态徽标」,不决定可见性。
**理由**:交易被月账单对账后 `source` 从 daily 翻成 bill;若按 source 过滤,它会从按日视图消失。按日期窗口则永久留在其发生日。
**跨度**:最近优先(默认窗口如 45 天),支持向前翻阅全部历史。

### D3: 覆盖度追踪 —— 让日结可信

**问题**:转发中断/服务器停机 → 某天日推邮件没收到 → 那天数据残缺,界面看不出。现有 `imap_last_uid` 只保证邮件不丢,不记录「哪些自然日已覆盖」。
**方案**:每封日推邮件自带日期头(`YYYY/MM/DD 您的消费明细如下`),解析时记录该自然日为「已覆盖」。存储位置见 D4。
**用途**:
- 按日单元标「已关账 ✅ / 有缺口 ⚠」
- 缺口处提示「这天没收到日推,数据可能不全」+ 支持手动补拉
- 汇总总额若含缺口日,标注「⚠ 含缺口,数字可能偏低」

### D4: 覆盖度存储 —— Setting 键 `daily_covered_dates`(已定稿)

**决定**:选项 A —— Setting 表存 `daily_covered_dates`,值为 JSON 排序日期数组(`["2026-08-07","2026-08-08",...]`)。
**理由**:轻量、复用现有表、无需 migration。已覆盖日集合足够驱动「已关账/缺口」判断(缺口 = 窗口内不在集合中的日期)。
**升级路径**:若数据量增长或需按日审计(覆盖时间/来源 UID),再迁到独立 `DailyCoverage` 表。
**否决**:选项 B(新表)—— 当前需求下过重。

### D5: 陈旧未对账 —— 人工干预

**规则**:日推插入但月账单长期未确认(`source="daily"` 且超过阈值天数如 45 天仍无对账)的交易,UI 提供删除/清理入口,由用户判断(可能是退款/撤销/银行未计)。
**理由**:自动删除有误删风险;人工干预安全。

### D6: 对账毕业高亮 —— 留痕字段 `graduatedFromDaily`(已定稿)

**决定**:Transaction 新增 `graduatedFromDaily Boolean @default(false)`。月账单对账一笔原 source="daily" 的交易时,置为 `true`。月账单 Tab 据此高亮「日推带标」。
**理由**:显式字段语义清晰、稳定;不依赖「`txTime` 非空」这类隐式信号(若未来月账单也带时间就失效)。
**否决**:复用 `txTime` 非空 —— 脆弱,见 Risks。

### D7: cron 每早自动关账

**方案**:部署侧系统 cron 每早调 `npm run ingest`(如 `7 8 * * *`),自动给昨天关账。应用侧不内建 scheduler(见已合并 design 的 Non-Goals)。

## Open Questions(实现前定稿)

- D4:覆盖度存 Setting 还是新表?
- D6:「日推毕业」判定依据 —— 新字段留痕 vs 复用 `txTime` 非空?

## Risks / Trade-offs

- **[日推毕业判定用 txTime]** 若未来月账单也带时间,该信号失效 → 倾向显式留痕字段更稳妥,D6 定。
- **[覆盖度误判]** 「当天无消费」的日推邮件无交易行但仍应记为「已覆盖」→ 覆盖度记录须基于邮件收到(日期头),非基于是否有交易。
- **[窗口性能]** 按日聚合全历史可能慢 → 默认窗口 + 分页往前翻。
